# Программа тестирования — AI-QA sandbox (Medusa v2)

> Статус: план утверждён, работа по этапам начинается в новой сессии.
> Ничего из ранее написанного по результатам (находки, гипотезы, выводы) не считается истиной —
> всё перепроверяется с нуля в рамках соответствующего этапа.

## 1. Цель и рамки

Найти максимум реальных дефектов в sandbox-магазине (Medusa v2 бэкенд + Next.js storefront + Medusa Admin)
через AI-подходы: агентное исследование, MCP-инструменты, детерминированное подтверждение находок.

Порядок этапов жёсткий: **API → UI → нефункциональное**. Требований нет — базовая линия строим сами.

## 2. Принципы процесса

1. **Аналитический вход перед каждым этапом.** Этап начинается не с действий, а с анализа:
   какая база сравнения (официальная документация Medusa v2 + наблюдаемое поведение эталонных ожиданий),
   какие гипотезы, какие области риска приоритетны. Подтверждение плана этапа пользователем — обязательно.
2. **Два чекпойнта на этап.** Первый — после анализа (согласие на план этапа), второй — после
   выполнения (согласие на результаты и дефекты до внесения в реестр).
3. **Базовая линия двойная:** (а) внешняя документация Medusa v2 Store/Admin API;
   (б) наблюдаемое поведение системы и её внутренняя согласованность (Store ↔ Admin ↔ UI).
4. **Находка ≠ дефект**, пока не подтверждена детерминированно: повторяемое воспроизведение +
   сырые артефакты (запрос/ответ, HAR, трейс, скриншот).
5. **Исследование — агентом, подтверждение — детерминированным кодом.** Агент ничего не «чинит»
   и не делает деструктивных действий в чужом sandbox.

## 3. Доступ к цели (окружение)

Домен `*.fly.dev` блокируется DNS-фильтром провайдера на этой машине (детали: `docs/00-environment.md`).
Харнесс в `config/targets.sh` привязывает домен к реальному IP через DoH (`--resolve`) — работает и здесь,
и на чистых машинах. Для UI-контура А (живой браузер) обход делает сам браузер (DoH включён пользователем).
На 28.09.2026 блокировка в текущей сети не проявляется (DNS отдаёт реальный IP `66.241.125.52`), харнесс сохранён на случай возврата.

## 4. Два контура

| Контур | Инструменты | Назначение |
|---|---|---|
| **А — живой браузер** | agent-browser 0.31.1 + Chrome for Testing 150 (headed), сессия `aiqa`; отдельный QA-профиль | Исследование UI как реальный пользователь: сессия, куки, реальный рендер, консоль, сеть |
| **Б — изолированный Playwright** | Playwright + отдельный Chromium | Детерминированные проверки, трейсы, HAR, повторяемость, CI-пригодность |

Исследование делается в контуре А; каждая находка переносится в контур Б как проверяемый сценарий.

## 5. Стек и язык (решено 27.09.2026)

- **Основной язык — TypeScript/Node.** Причины: Playwright и все MCP-серверы нативны в TS;
  у Medusa есть официальный JS SDK — используем как эталонного клиента для дифференциальных
  проверок «SDK ↔ сырой HTTP»; тест-агенты Playwright (planner/generator/healer) генерируют TS;
  один язык покрывает API, UI и нефункциональный слой.
- **Bash-скрипты** (`config/targets.sh`, `scripts/*.sh`) остаются для ручного зондирования в терминале.
- Schemathesis — как готовый CLI-инструмент (pip), собственный код на нём не пишем.
- npm-окружение проекта ставится на этапе 1 (Playwright, MCP-пакеты, JS SDK Medusa,
  ajv/zod для контрактных проверок; chromium для контура Б — после подтверждения).
  Статус 28.09.2026: установлено — `@playwright/test` 1.63.0 + Chromium 1243, `@medusajs/js-sdk`, `zod`, `ajv`, `tsx`.

## 6. Этапы

- **Этап 0 — подготовка (эта сессия):** план, структура репо, шаблоны, пуш.
- **Этап 1 — базовая линия и реестры:** карта эндпоинов и страниц, реестр требований-по-наблюдению,
  реестр допущений, приоритизация областей риска. Выход: согласованная карта проверки.
- **Этап 2 — API:** контрактные проверки Store API, дифференциальное тестирование Store ↔ Admin,
  негативные и граничные входы, фаззинг (Schemathesis), поведение ошибок.
- **Этап 3 — UI:** агентное исследование storefront и админки (контур А), состояния, формы, чекаут,
  мобильный вьюпорт; перенос находок в контур Б.
- **Этап 4 — нефункциональное:** производительность и стабильность, доступность (axe), заголовки
  безопасности, rate-limit, поведение под повторной нагрузкой.
- **Этап 5 — сводный отчёт:** консолидация дефектов, вердикт, рекомендации.

## 7. Области риска (реестр областей)

1. Каталог и пагинация (`count/offset/limit`, фильтры, сортировка).
2. Корзина: создание, элементы, количества, границы.
3. Промокоды и скидки.
4. Регионы, валюты, налоги.
5. Доставка и способы оплаты.
6. Чекаут: сессии, завершение заказа, повторные вызовы.
7. Аутентификация покупателя и профиль.
8. Инвентарь и доступность вариантов.
9. Админка: права, изоляция Store/Admin.
10. Контракты и обработка ошибок API.
11. UI-состояния: пустые состояния, ошибки, загрузки, консистентность данных с API.
12. Доступность, SEO, заголовки.
13. Производительность и стабильность ответов.
14. Безопасность: CORS, заголовки, rate-limit, инъекции в поля.

## 8. Реестры и дефекты

- Реестр требований/кейсов/допущений: `registry/` в репо + GitHub Issues + GitHub Projects
  (для Issues/Projects нужен fine-grained токен пользователя — попросить на этапе 1).
- Дефекты: по одному Markdown-багрепорту (`reports/bugs/BUG-XXX.md`) + запись в реестре.

## 9. Отчётность

- **Классический багрепорт** — `reports/templates/bug-report.md`: ID, заголовок, severity/priority,
  окружение, предусловия, шаги, ожидаемо/фактически, артефакты, воспроизводимость.
- **Сводный отчёт прогона** — `reports/templates/run-report.md`: охват, метрики, таблица проверок,
  список дефектов, вердикт.
- Машинные прогоны (контур Б) — при желании позже добавим Allure.

## 10. Предохранители агента

- Allowlist действий: без покупок реальными платёжными методами, без удаления чужих данных,
  без массовых мутаций.
- Лимиты: шагов и времени на исследование; каждое действие логируется.
- Каждый найденный баг — с сырым артефактом (скриншот / HAR / запрос-ответ), а не «словами агента».
