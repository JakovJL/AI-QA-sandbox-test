## Предусловия

- Доступен Store API с валидным `x-publishable-api-key`.

## Шаги воспроизведения

1. `GET /store/products?limit=-1`.
2. `GET /store/products?offset=-1`.
3. Для сравнения поведения валидации: `GET /store/products?limit=abc` и `?offset=abc`.

## Ожидаемый результат

Отрицательные значения — невалидный ввод: ответ 4xx `invalid_data` с понятным сообщением
(как для строкового ввода). Основание: семантика ошибок Medusa v2 (`invalid_data` → 400), Общий принцип:
пользовательский ввод не должен приводить к 5xx.

## Фактический результат

- `/store/products?limit=-1` → **HTTP 500** `{"code":"unknown_error","type":"unknown_error","message":"An unknown error occurred."}`
- `/store/products?offset=-1` → **HTTP 500** (то же тело).
- Контроль: `limit=abc` / `offset=abc` → **HTTP 400** `{"type":"invalid_data","message":"Invalid request: Expected type: 'number' for field 'limit', got: 'abc'"}`.

Т.е. проверка типа есть, проверки диапазона (неотрицательность) нет — значение доходит до слоя данных и роняет обработчик.

## Артефакты

- Проверки: `tests/api/store-input-validation.spec.ts` (2 падения — репродьюсеры; строковые контроли проходят).
- Сырые ответы: `reports/artifacts/store-input-validation/invalid-*.json`.

## Примечания

- 500 на клиентский ввод искажает мониторинг (выглядит как падение сервиса) и не даёт клиенту понять ошибку.
- Рекомендуется проверить диапазонные ограничения и на других числовых параметрах Store/Admin (кандидат на расширение при фаззинге 2.5).
- HTTP-семантика: спека не задаёт `minimum` для `limit`/`offset`, поэтому основание — обработка ошибок, а не формальное нарушение схемы.
