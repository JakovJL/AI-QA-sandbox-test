## Предусловия

- Доступен Store API с валидным `x-publishable-api-key`.

## Шаги воспроизведения

1. `GET /store/products?order=` (пустое значение).
2. `GET /store/products?order=xyz` (несуществующее поле сортировки).
3. `GET /store/regions?order=`, `GET /store/collections?order=`, `GET /store/return-reasons?order=`.
4. Контроль: `GET /store/products?order=title` — валидная сортировка.

## Ожидаемый результат

Невалидное значение `order` → 4xx `invalid_data` с понятным сообщением.
Основание: общая семантика ошибок Medusa v2 (док: `invalid_data` → 400; в спеке для list-операций объявлены 400/422);
принцип «пользовательский ввод не приводит к 5xx».

## Фактический результат

- `order=` / `order=xyz` → **HTTP 500** `{"code":"unknown_error","type":"unknown_error","message":"An unknown error occurred."}`
  на `/store/products`, `/store/regions`, `/store/collections`, `/store/return-reasons` (5/5).
- Контроль: `order=title` → 200.

## Артефакты

- Проверки: `tests/api/store-input-validation.spec.ts` (кейсы `invalid-order`, 5 падений-репродьюсеров).
- Артефакты ответов: `reports/artifacts/store-input-validation/invalid-order-*.json`.
- Фаззинг: `reports/artifacts/schemathesis/run.log` (11 Server error → изоляция), `summary.md`.

## Примечания

- Тот же класс, что BUG-002 (`limit`/`offset`) и BUG-004 (date-фильтры): невалидный query-параметр доходит до слоя данных
  и приводит к 500 вместо 400. Вероятен общий корень — отсутствие валидации значений (тип проверяется, значение — нет).
- Затронуты все проверенные list-эндпоинты с `order`; полный список эндпоинтов с `order` — в спеке (`vendor/openapi/store.openapi.full.yaml`).
