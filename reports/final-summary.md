## 1. Цель и рамки

Найти максимум реальных дефектов в sandbox-магазине (Medusa v2 backend + Next.js storefront dtc-starter + Medusa Admin)
агентными методами (контуры А — живой браузер, Б — Playwright) с детерминированным подтверждением каждой находки.

- Требований нет: базовая линия — официальные OpenAPI-спеки Medusa v2 (вендорены, тег v2.21.1) + наблюдаемая
  согласованность Store ↔ Admin ↔ UI; спорное сверялось с несколькими версиями спек.
- Дисциплина процесса: аналитический вход и чекпойнты на каждый этап, сырые улики (JSON/HAR/скриншоты),
  без «починок» в песочнице, лимиты мутаций (малые тестовые данные: корзины/заказы, регион `zzz` удалён).

## 5. Что проверено и признано чистым

- Корзина/чекаут happy-path: полный флоу (API и UI), идемпотентный повторный `complete`, резервы инвентаря,
  oversell → 400, границы количеств (TC-006/014/022).
- Store ↔ Admin согласованность: товары, цены, варианты, инвентарь (дифф 5/5); Admin `count` корректен (TC-008).
- Промо 10% (10→9), offset-пагинация, трансфер заказа (accept требует токен владельца), адреса по спеке,
  `CreateCart` без региона (TC-029).
- Границы аутентификации: customer JWT не действует в Admin API, admin-токен — в customer-маршрутах, подделка
  токена → 401 (TC-037).
- Безопасность-наблюдения: CORS не отражает чужой Origin (Store/Admin), TRACE выключен, служебные пути
  (`/.git/config`, `/metrics`, `/debug`, `/server-status`) не раскрываются, `/health` → 200 «OK» (ожидаемо).
- Производительность: 2×10 замеров на 9 эндпоинтов — 0 ошибок/таймаутов; медианы 94–409 мс, p95 ≤ 617 мс;
  «рваная стабильность» из этапа 1 не воспроизвелась (TC-038).

## 6. Наблюдения (не дефекты)

- Троттлинга на `/auth/customer/emailpass` нет (6×401 без 429) — по A-005 в Medusa v2 клиентского rate-limit нет.
- `http://<host>` (порт 80) не отвечает (`socket hang up`) — инфраструктура fly/CDN, вне кода приложения (по решению не заводили).
- Cookie `_medusa_cache_id` без HttpOnly/Secure/SameSite (нечувствительный кэш-id); `x-powered-by: Next.js/Express`.
- Артефакт песочницы `/blocking-fault.js` — приманка (A-003); правки данных после сидинга — «посаженные» (A-004).

## 7. Вердикт

Функциональное ядро магазина работоспособно: каталог, корзина, чекаут (включая идемпотентность и инвентарь),
согласованность Store ↔ Admin, границы аутентификации — подтверждены. Основные проблемы сосредоточены в трёх зонах:
(1) обработка невалидного/граничного ввода → HTTP 500 в Store и Admin API и приём несуществующей валюты;
(2) веб-конфигурация безопасности — нет базовых заголовков, страницы фреймятся, soft-статусы маскируют ошибки;
(3) доступность — системные нарушения WCAG AA на витрине и в админке. Производительность и стабильность — в норме.

## 8. Рекомендации (по приоритету)

1. **P1 — 500-семейство:** валидация значений query/body (диапазоны, пустые строки, типы) в Store и Admin API;
   фикс `count` в `/store/products`; обработка `calculate` для `flat`-опций (BUG-001…004, 009–011).
2. **P1 — безопасность периметра:** HSTS/CSP (`frame-ancestors`)/XFO/XCTO на витрине, `/app` и API; редирект :80→:443 (BUG-013).
3. **P1 — dev-конфиг:** исключить `127.0.0.1`-адреса из прод-сборки витрины (BUG-005).
4. **P2 — доступность:** метки форм, доступные имена кнопок, `alt`, контраст, навигация (BUG-014…018);
   часть фиксов — в апстримах (dtc-starter, Medusa Admin).
5. **P3 — HTTP-семантика и UI-мелочи:** 404 для неизвестных заказов/путей, title категорий, дубль select,
   мёртвая ссылка (BUG-006…008, 012, 019).
6. **Апстрим:** BUG-007/008/012/018 → `medusajs/dtc-starter`; admin-часть BUG-014…017 → `medusajs/medusa` (admin).
7. **Регрессия:** держать сьют в CI с allowlist ожидаемых падений (по мере фиксов снимать); perf-baseline —
   как ориентир, axe — расширять (mobile уже включён).

## 9. Ограничения и допущения

- A-001: точная версия песочницы не раскрывается (≈2.21.x); A-002: витрина — сборка dtc-starter без изменений UI;
  A-004: часть данных «посажена» после сидинга; A-005: отсутствие клиентского rate-limit — свойство v2.
